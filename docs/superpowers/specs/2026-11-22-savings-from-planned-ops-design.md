# Накопления под плановые покупки

Дата: 22 ноября 2026

## Задача

Сейчас накопления планируются руками: заводишь цель, а потом в каждую клетку
бюджета вбиваешь, сколько отложить в этом месяце и сколько взять. Ни цены
покупки, ни её даты, ни тем более периодичности система не знает — она
просто хранит введённые числа.

Нужно наоборот: сказать «страховка 30 000 в марте, каждый год», и чтобы
бюджет сам показал, сколько откладывать каждый месяц, а в марте — сколько
взять из отложенного.

**Главная ценность — цифра «сколько нужно откладывать» в бюджете.**
Распоряжение деньгами остаётся ручным: владелец постоянно перекидывает
суммы между целями, и автоматизировать это он не просит.

## Что уже есть

Две половины решения существуют и не связаны.

**Цели** (`goals`) — копилки: название, валюта, целевая сумма. Дат нет.
Помесячные планы лежат в `budget_goal_plans` («Отложить») и
`budget_goal_withdrawal_plans` («Взять из отложенного») — обе таблицы
заполняются только вручную.

**Шаблоны плановых операций** (`operation_templates`) — ровно та
повторяемость, которой не хватает целям: сумма, правило повторения
(`freq`, `interval`), генератор вхождений с датами. Используются для
«ожидаемых платежей», с накоплениями не связаны.

**Желания** (`wishes`) тоже умеют цену, дату и признак повторения, но это
отдельная ветка без денег и без экрана в новом интерфейсе. В этой задаче
их не трогаем.

Вывод: повторяемость переизобретать не нужно. Нужно связать шаблон
плановой операции с целью и научить бюджет считать график.

## Решения

Приняты в обсуждении, зафиксированы здесь, чтобы не переигрывать молча.

| Вопрос | Решение |
|---|---|
| Единица планирования | Шаблон плановой операции + привязка к цели |
| Цель | Выбирается вручную; несколько покупок могут копиться в одну |
| Размер взноса | Сумма ÷ число месяцев до даты, равномерно |
| После покупки | Цикл начинается заново сам, от следующего вхождения |
| Списание при покупке | Не автоматизируем — перераспределение остаётся ручным |
| Ручной план против расчётного | Расчётный подставляется, ручной перебивает |
| Отложил меньше плана | Вопрос в бюджете: поднять взнос или сдвинуть дату |

## Устройство

### Данные

Одно новое поле:

```
operation_templates.saving_goal_id: int | None   # -> goals.goal_id
```

Заполнено — значит под эту операцию копим. Отдельный булев признак не
нужен: он мог бы противоречить привязке, а так состояние одно.

**Расчётный план нигде не хранится.** Он выводится из шаблона при сборке
бюджета. Это важно: иначе правка суммы или даты оставляла бы в базе
устаревшие цифры, и пришлось бы их догонять.

### Расчёт взноса

Для шаблона с привязанной целью:

```
окно накопления = месяцы от текущего до месяца покупки НЕ включая его
взнос = сумма операции ÷ число месяцев в окне
```

Покупка в марте → копим апрель–февраль, в марте берём. Если до покупки
остался один месяц, весь взнос приходится на него.

Если к цели привязано несколько шаблонов, их взносы **складываются** в
одну строку «Отложить» по этой цели.

### Как это попадает в бюджет

`BudgetMatrixService._build_goal_section` для каждой клетки берёт план так:

1. запись в `budget_goal_plans` для этого месяца и цели — если есть, она и есть план;
2. иначе — сумма расчётных взносов по привязанным шаблонам.

Расчётное значение показывается серым и помечается как расчётное, чтобы
было видно, откуда взялось число и что его можно перебить.

В месяце покупки по той же схеме заполняется «Взять из отложенного» на
полную сумму операции.

### Перезапуск цикла

Отдельного механизма не требуется. Расчёт всегда смотрит на **следующее
невыполненное вхождение** шаблона. Выполнил мартовскую страховку —
следующее вхождение становится мартовским в следующем году, окно
накопления пересчитывается само.

Это прямое следствие того, что расчётный план не хранится.

### Отставание

Отставание считается **по цели целиком**, а не по отдельной покупке:
факт «Отложить» нельзя разнести между несколькими покупками, которые
копятся в одну копилку.

Условие: в закрытом месяце факт по цели меньше плана больше чем на
порог (возьмём те же 500 ₽, что и в подсказках бюджета).

Показывается в карточке подсказок бюджета — она уже есть — с тремя
действиями:

- **Поднять взнос** — дата держится, недобранное размазывается по
  оставшимся месяцам. Технически: в `budget_goal_plans` записывается
  пересчитанная сумма на оставшиеся месяцы, то есть ручной план,
  посчитанный за пользователя.
- **Сдвинуть дату** — взнос прежний, вхождение переносится вперёд.
  Переиспользуется существующий перенос вхождения.
- **Оставить как есть** — вопрос закрывается до следующего месяца.

Для страховки дату не сдвинешь, для ноутбука можно — поэтому выбор, а не
одно действие.

## Экраны

**Шаблон плановой операции** — в модалке появляется «Копить заранее» с
выбором цели. Под ним подсказка с расчётом: «Будет откладываться по
2 500 ₽ в месяц, 12 месяцев до марта».

**Бюджет** — расчётные взносы видны в строке «Отложить» по цели.
Отставание приезжает в карточку подсказок.

**Цель** — список привязанных покупок с датами, чтобы было понятно, из
чего складывается взнос.

## Границы

Не делаем в этой задаче:

- автоматический перевод денег при покупке — владелец перераспределяет сам;
- связь с «желаниями» — отдельная ветка, её судьба не решена;
- разнесение факта между несколькими покупками одной цели — отставание
  показывается по цели целиком;
- неравномерные графики (больше в начале, меньше в конце) — только
  равномерный.

## Риски

**Несколько покупок в одной цели.** Взносы складываются, отставание
общее. Если выяснится, что так непонятно, следующий шаг — рекомендовать
одну цель на одну покупку, а не усложнять разнесение.

**Расчёт на лету.** Сборка бюджета станет чуть тяжелее: добавится выборка
шаблонов с привязкой и их ближайших вхождений. Шаблонов единицы, влияние
должно быть незаметным, но проверить на реальных данных стоит.

**Пересчёт пишет ручной план.** После «Поднять взнос» клетки перестают
быть расчётными и замирают. Это осознанно — иначе кнопка ничего бы не
делала, ведь расчёт и так самокорректируется, — но пользователь должен
видеть, что значение стало ручным.

## План работ

1. Миграция и поле `saving_goal_id` в шаблоне операции; API создания и
   правки шаблона принимает его.
2. Модуль расчёта: по account_id и месяцу возвращает взносы по целям и
   суммы к снятию. Чистая функция, тесты на окно, перезапуск цикла,
   несколько шаблонов в одной цели, покупка в следующем месяце.
3. Подключение к `BudgetMatrixService`: расчётное значение как подложка
   под ручное.
4. Признак «расчётное» в ответе API и серое отображение в бюджете.
5. Правило отставания в `budget_insights` и три действия в карточке.
6. Интерфейс шаблона: выбор цели и подсказка с расчётом.
7. Список привязанных покупок в карточке цели.
