# Бэкапы и восстановление FinLife/Centricore

Цель простая: **не потерять данные**. Шифрования нет (данные не секретные) — значит нет ключей и нет риска «потерял ключ → потерял бэкапы». Просто держим копии в трёх местах (схема 3‑2‑1).

| Копия | Где | От чего спасает |
|---|---|---|
| 1. Локальный дамп | сервер `/opt/centricore/backups/*.sql.gz` | кривая миграция, порча данных |
| 2. Telegram-канал | приватный канал (через бота) | вайп/потеря сервера |
| 3. Твоя машина | `pull_backups.ps1` тянет к тебе | вайп/потеря сервера + потеря Telegram |
| 4. (опц.) GitHub | приватный репо, последние N дампов | ещё одна независимая off-site копия |

Один запуск `backup_prod_db.sh` = сделать сжатый дамп (копия 1) + отправить его в Telegram (копия 2). Твой компьютер тянет копию к себе отдельно (копия 3).

> Канал держи **приватным**: дамп внутри незашифрованный.

---

## Разовая настройка

### 1. Telegram-канал (копия 2)

1. В Telegram создай **приватный канал** (только ты).
2. Бот: возьми существующего или заведи нового у **@BotFather** (`/newbot` → получишь **токен** вида `123456:AA...`).
3. Добавь бота **администратором** канала (право «Публиковать»).
4. Узнай **ID канала** (`chat_id`): напиши что-нибудь в канал, потом открой (при блокировке — через прокси `--proxy socks5h://...`):
   ```bash
   curl "https://api.telegram.org/bot<ТОКЕН>/getUpdates"
   ```
   Найди `"chat":{"id":-100XXXXXXXXXX,...}` — это `chat_id` (с минусом, начинается на `-100`).
5. Впиши в `/opt/centricore/.env`:
   ```
   BACKUP_TG_BOT_TOKEN=123456:AA...
   BACKUP_TG_CHAT_ID=-100XXXXXXXXXX
   # TELEGRAM_PROXY уже есть — бэкап использует его же
   ```
> Лимит файла в Telegram — ~50 МБ. Дамп финансов гораздо меньше; если перерастёт — скрипт предупредит в канал, а копии 1 и 3 продолжат работать.

### 2. Расписание на сервере (cron)

```bash
chmod +x /opt/centricore/backup_prod_db.sh
crontab -e
# каждый день в 03:30 по времени сервера:
30 3 * * * /opt/centricore/backup_prod_db.sh >> /opt/centricore/backups/backup.log 2>&1
```
Проверить сразу: `/opt/centricore/backup_prod_db.sh` — в канал должны прийти файл `.sql.gz` и «✅ Бэкап ок».

### 3. Пул на свою машину (копия 3, Windows)

1. Настрой SSH-ключ к серверу (чтобы `ssh root@45.144.30.5` заходил без пароля).
2. Открой `scripts/pull_backups.ps1`, при необходимости поправь `$Server`.
3. Task Scheduler → задача «ежедневно», действие:
   ```
   powershell.exe -ExecutionPolicy Bypass -File "C:\путь\scripts\pull_backups.ps1"
   ```
   Файлы лягут в `%USERPROFILE%\FinLifeBackups`.

### 4. (опц.) Приватный git-репозиторий (копия 4)

Git плохо хранит ежедневные бинарники (репо пухнет). Поэтому держим **отдельный
приватный** репо и каждый раз кладём только последние N дампов, **сплющивая
историю** (orphan-снапшот) — репозиторий остаётся маленьким. Скрипт откажется
пушить, если в папке репо есть посторонние файлы (защита от «снести репо с кодом»).

1. Создай на GitHub **новый приватный** репозиторий (напр. `finlife-backups`), пустой.
   > ⚠️ Именно ОТДЕЛЬНЫЙ, не репо с кодом. Данные хоть и не секретные — репозиторий всё равно **приватный**.
2. Дай серверу право пуша: в репо → Settings → Deploy keys → добавь публичный SSH-ключ сервера с галкой **Allow write access** (или используй PAT).
3. Клонируй его на сервер и впиши путь в `.env`:
   ```bash
   git clone git@github.com:<ты>/finlife-backups.git /opt/centricore/backup-git
   ```
   ```
   BACKUP_GIT_DIR=/opt/centricore/backup-git
   # BACKUP_GIT_BRANCH=main   # по умолчанию main
   ```

Дальше ничего не нужно — тот же `backup_prod_db.sh` после дампа зеркалит последние
N файлов в этот репо. В сообщении в Telegram появится «· git ок».

## Восстановление

Из любого `.sql.gz` (с сервера, из Telegram или из папки на компе):
```bash
# положить файл на сервер, затем:
/opt/centricore/restore_prod_db.sh /opt/centricore/backups/prod_YYYYmmdd-HHMMSS.sql.gz
```
Скрипт сам распакует и зальёт. **Перезаписывает текущую БД** — сначала убедись, что берёшь правильный файл.

Полное восстановление на новом сервере: развернуть проект (`git clone`, `.env`, `docker compose ... up -d`), закинуть любой `.sql.gz` и выполнить ту же команду.

---

## Проверка (раз в квартал)

Бэкап без проверенного восстановления — это надежда, а не бэкап. Раз в квартал восстанови свежий `.sql.gz` во временную БД и глянь, что данные на месте. Поставь календарное напоминание.

## Если позже данные станут чувствительными

Тогда добавим шифрование (`age`, публичный ключ на сервере, приватный — у тебя) — скрипты к этому готовы расширяться. Пока не нужно.
